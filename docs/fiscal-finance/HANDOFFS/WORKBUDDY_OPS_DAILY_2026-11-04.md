### 2.2 NOOP_TERMINAL 的根因（已定位到代码行）

`tools/ollama-understand-nightly-r3.mjs`：

```js
function isTerminal(status) {                    // L249-251
  return status === "COMPLETED" || status === "REVIEW_REQUIRED";
}
...
if (existing && isTerminal(existing.status)) return { outcome: "NOOP_TERMINAL", state: existing };  // L410
```

第 410 行在**日期判断之前**、且**不比较 `attemptDateShanghai`**。state 只有单份文件，一旦 11/1 写成 `COMPLETED`，此后任意日期的运行都直接返回 `NOOP_TERMINAL`。

**结论：11/2–11/4 的连续 NOOP_TERMINAL 不是故障，是该有界 pilot"单终态一次性"设计的必然结果；它也确实不构成每日连续运行证据。** 附带一处证据短板：`logs/cron.log` 每次只追加终态词、**不带时间戳**（共 7 行：`REVIEW_REQUIRED`×3、`COMPLETED`、`NOOP_TERMINAL`×3），日期只能靠 state mtime 与结果文件名反推，不足以独立支撑跨日时间线。

### 2.3 按日接续方案（待批准，未实施）

目标：保留 11/1 已完成的终态证据，同时让每日运行可以真实发生；不得删除 `COMPLETED`/失败 state 来触发重跑。

| 要点 | 设计 |
|---|---|
| 状态载体 | 改为按日：`state/…-r5/2026-11-05.json`，历史文件只读保留；或单文件内加 `days: {dateKey: {status, runId, hashes}}` 映射 |
| 同日幂等 | `attemptDateShanghai === today` 且已终态 → `NOOP_ALREADY_ATTEMPTED_TODAY`（现有 SKIPPED_* 已有此逻辑，扩到 COMPLETED） |
| 跨日边界 | 日期键用 `Asia/Shanghai`，02:00 窗口内只允许一个 `dateKey`，窗口外 `NOOP_OUTSIDE_WINDOW` 不变 |
| 每日预算 | 显式 `dailyMaxRequests`（现为 8）+ 累计上限，超限写 `REVIEW_REQUIRED` 而非静默截断 |
| 历史保留 | 旧 state 与 results 全部只读留存，不删除、不改写哈希 |
| 必要测试 | ①同日二次运行 → `NOOP_ALREADY_ATTEMPTED_TODAY`；②跨日运行 → 新 runId 且旧 state 不变；③超预算 → 熔断；④state 损坏 → `REVIEW_REQUIRED`；⑤锁复用同一 inode（`76:161641`）不被替换 |

风险提示：这是**运行设计变更**，需按 §九 走可审阅版本 + 备份 + 回退，且安装后仍要等真实新日期运行才能算证据。**未获批准前不动 NAS 脚本。**
